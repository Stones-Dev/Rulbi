# T1.4 — Benchmark de sanity, 50k live streams Xtream

**Tarea**: [Cliente Xtream (TDD)](https://app.notion.com/3a3df75619268103ade2f8523dab79f1)
(*Tareas — IPTV*, Sprint 2). No es un "Hecho cuando" con cifra propia en
Notion (a diferencia de T1.5b) — es el micro-benchmark de sanity que el
plan de T1.4 pidió antes de cerrar la tarea, mismo espíritu que
`packages/protocols/test/m3u/m3u_parser_benchmark_test.dart`: confirma que
`XtreamClient.importChannels()` no se cae ni se cuelga con un panel
grande, y documenta dónde anda su tiempo/memoria/jank frente al
presupuesto de RNF-01.

**Veredicto: dentro de presupuesto**, con un hallazgo real que cambió el
diseño antes de cerrarse (ver "Iteración" abajo): 50.000 canales live en
**~355-362 ms** (varias corridas), jank máximo **36-47 ms**, **1-3 ticks
de ~20** por encima del presupuesto de frame de 32 ms — no cero, pero un
pico aislado durante el fetch inicial, no un patrón sostenido.

---

## Qué mide este benchmark

`packages/protocols/test/xtream/xtream_benchmark_test.dart`, contra dos
fuentes:

1. Los 9 fixtures reales de T1.1 (`dialect_o0zz/`) — debe ser ruido
   (< 1 s).
2. Un JSON **sintético** de 50.000 live streams
   (`tool/generate_bench_xtream.dart` → `packages/protocols/test/fixtures/
   xtream/large/bench_50k_live_streams.json`, gitignored, regenerable bajo
   demanda) — no hay catálogo Xtream real de ese tamaño para replicar (a
   diferencia de T1.5b, que sí tenía el índice completo de iptv-org).
   Distribuido en 20 categorías, con variación real de `stream_icon`/
   `epg_channel_id` ausentes (1 de cada 7 y 1 de cada 11 respectivamente).

Solo mide `XtreamClient.importChannels()` (fetch simulado vía
`FakeXtreamTransport` + decodificación + mapeo a `Channel`) — **no** el
pipeline completo con `packages/data` (eso sería una tarea aparte, al
estilo de T1.5b sobre M3U, no pedida por T1.4).

## Iteración: por qué la decodificación JSON acabó en un `Isolate`

La primera versión de `importChannels()` (T1.4, antes de este benchmark)
solo cedía el event loop **durante el bucle de mapeo** (`XtreamLiveStream`
→ `Channel`, cada `cessionInterval` canales — mismo patrón que corrigió el
jank real de T1.6b), dejando el `jsonDecode` del cuerpo de la respuesta
como una llamada síncrona normal en `_getJsonBody`, igual que en
`auth()`/categorías (donde el cuerpo es pequeño y no importa).

Primera corrida del benchmark contra el fixture de 50k (~14.8 MB de JSON):

```
50000 canales, 0 descartes, 336 ms, jank máx 149 ms, ticks > 32 ms: 1/12.
```

**149 ms de jank máximo** — casi 10 frames a 60 fps de un solo tirón,
justo donde se esperaría: el `utf8.decode` + `jsonDecode` de 14.8 MB
corriendo síncrono en el isolate llamador, antes de que el bucle de
mapeo (que sí cedía) tuviera oportunidad de ceder nada. Exactamente el
riesgo #2 documentado en el plan de T1.4 ("Respuestas de >100 MB en
paneles gigantes... decode en isolate").

**Corrección aplicada** (antes de cerrar la tarea, no como deuda futura):
`_getJsonBody` ahora hace el sniff de "¿esto es HTML/vacío?" sobre los
**bytes crudos** (mira los primeros 64 bytes, nunca decodifica el cuerpo
completo solo para mirarlo) y ejecuta `utf8.decode`+`jsonDecode` dentro de
`Isolate.run(...)` — un decode de una sola vez (no un worker con streaming
de mensajes como `parseM3u`, innecesario aquí porque ya se tiene el cuerpo
completo en memoria de la petición HTTP). Re-medido tras el cambio:

```
355-362 ms (3 corridas), jank máx 36-47 ms, ticks > 32 ms: 1-3 de ~20.
```

El pico de jank bajó de **149 ms a ~40 ms** — una mejora real, no
completa. El residuo restante se atribuye al propio *round-trip* de
`Isolate.run` (copiar ~14.8 MB de bytes hacia el isolate nuevo + copiar de
vuelta la estructura `List<Map<String, Object?>>` ya decodificada, ambas
operaciones de por sí no gratuitas) — no al `jsonDecode` en sí, que ahora
corre fuera del isolate llamador. Documentado como límite conocido, no
oculto: si un futuro benchmark con datos más realistas (o en hardware de
gama baja, RNF-04) muestra que este residuo importa, la vía razonable es
mover también el mapeo a `Channel` dentro del mismo isolate (evitando
transferir la estructura JSON intermedia, solo los `Channel` ya
construidos) — no se ha hecho aquí por no ser una necesidad medida
todavía, mismo criterio de "medir antes de complicar" que ya siguió
T1.6b con el upsert diferencial.

## Reproducir

```powershell
dart run tool/generate_bench_xtream.dart      # genera el fixture de 50k (gitignored)
cd packages/protocols
dart test test/xtream/xtream_benchmark_test.dart
```

Se salta limpiamente (sin fallar) si el fixture no está generado. No es
gate de CI — mismo criterio que `m3u_parser_benchmark_test.dart`.

## Alcance no cubierto por este benchmark

- VOD/series no se miden a esta escala (los fixtures reales solo traen 1
  película y 1 serie) — `vodStreamToChannel`/`liveStreamToChannel` son la
  misma forma de función pura, sin motivo para esperar un comportamiento
  distinto, pero no está medido con volumen.
- No mide el pipeline completo con `packages/data` (upsert diferencial +
  FTS5) — ver nota de alcance arriba.
- Las cifras son de una máquina de desarrollo, no de un dispositivo Android
  TV/webOS de gama baja (RNF-04, spikes S1/S4) — el jank real en hardware
  restringido puede diferir.
